# 開発フロー1の振り返り（2026-10-14）

## 対象と方法

| 項目 | 内容 |
|---|---|
| 対象 | 開発フロー1（概念設計 → ドキュメント群 → Issue → 実装 → コードレビュー） |
| 目的 | スキルを使った開発フローの検証。できるだけ人が確認せずに進められるか |
| 根拠 | `git log`（49コミット）、`issues/`（22件）、`design/rounds/01〜18/review.md`、`docs/reports/test_coverage.md`、`docs/reports/2026-10-14-code-review.md` |
| 制約 | 作業時間、トークン量、人が介入した回数は記録がないため、定量評価していない |

## 結論

ドキュメントから Issue を作り、Issue 単位で実装を進める流れは、実装工程をほぼ自走させるのに十分に機能した。
コードレビューでは、実装はドキュメントにほぼ忠実と判定され、要対応の指摘は1件だった。

一方で、人の確認が入った時点で画面の導線に関する修正 Issue が6件（ドキュメント更新と実装の3組）発生した。
自動のセルフチェックは画面単位の見た目を評価していたが、利用者が操作を完了するまでの導線は評価していなかった。
また、デザインの自己採点は合格ラインの8点に張り付き、品質の差を示す情報として機能しなくなっていた。

次のフローでは、人が確認する時点を実装の後から実装の前（画面構成の段階）へ移し、レビュー結果を Issue に戻す工程を加えるとよい。

## 結果の概要

| 指標 | 値 |
|---|---|
| Issue | 22件（計画分 001〜015 と 004b、追加の 016〜021）。完了 21件、`doing` 1件（015 デプロイ） |
| コミット | 49件。Issue ごとにブランチを切り、`main` にマージ |
| テスト | 14ファイル、約125ケース（`it`／`test` の出現数） |

| コードレビュー | 要対応 1件、参考 5件 |

## 良かった点

### 上流ドキュメントから Issue までの連鎖

概念設計から Requirements、Architecture、Test Strategy、実装計画を経て Issue に至るまで、各段階が前段の決定を参照する形で作られた。
各 Issue は Background、Scope、Out of scope、受け入れ条件、テスト候補を持ち、実装者が上流を読み直さなくても着手できる単位になっていた。
001〜014 は、計画どおりの依存順で人の判断を挟まずに完了している。

### テストのシームを先に合意したこと

Test Strategy で「HTTP 境界と lib の純粋関数の2つだけでテストする」と合意したことで、モックの乱立やテスト方針の揺れが起きなかった。
行カバレッジ 94.72% のテストが実装と同時に積み上がり、後半の UI 変更（016〜021）でも既存テストが回帰の検知役として働いた。
テストが CSS クラスや DOM の構造に依存しない方針も、UI の作り直しでテストを壊さずに済んだ要因である。

### 仕様変更を「ドキュメント Issue → 実装 Issue」の組で処理したこと

人の確認で出た変更（作成ページの独立、投稿ボタン、返信フォームの簡略化）を、先にドキュメントを更新する Issue と実装する Issue の組に分けた。
その結果、ドキュメントと実装の乖離は小さく、コードレビューで見つかった不一致は Architecture の構成図の古さなど記述側の問題にとどまった。

### 止まるべき地点で止まったこと

004b では、セルフチェックが上限の5ラウンドに達した時点で、未達の内容を記録してユーザーの判断を仰いだ。
アプリ名や書体のように人が決めるべき事項も、Issue の中で「ユーザーと相談」と明示したため、エージェントが独断で決めずに済んだ。
「人に任せる判断」と「エージェントが進めてよい判断」を Issue の記述で区別できたことが、自走と安全性の両立につながった。

### 機械的に検査できる品質の安定

axe の違反、CSS とフォントの容量予算、`/_styleguide` の本番無効化など、機械で判定できる基準は最後まで守られた。
数値で判定できる基準は、自動化したフローでも劣化しにくい。

## 悪かった点と足りなかった点

### 人の確認後に導線の修正が6件発生した

016〜021 は、画面ごとの見た目ではなく操作の導線（どこから作成し、どこで返信するか）の修正である。
セルフチェックの評価対象は画面単位のスクリーンショットだったため、「スレッドを立てる」のような操作の流れは評価されていなかった。

原因の一部は上流にもある。
UI_GUIDELINES §4.2 で「作成フォームは一覧の後」と定めたのは、ドキュメント作成の段階である。
導線の判断が誤っていても、実装者とセルフチェックはその前提に従うため、実装が終わるまで誰も気付けない構造だった。

### 自己採点が合格ラインに張り付いた

Round 06 から Round 18 までの13ラウンドで、評価軸 A〜E はすべて8点、F と G はすべて9点だった。
合格基準を「全軸8点以上」としたことで、8点が「合格を意味する点」になり、品質の高低を区別する情報を失っていた可能性が高い。

独立したエージェントによる採点は 004b の Round 03 と 05 だけで行われた。
Round 03 では、独立採点が自己採点より1〜2点低い軸があった（インタラクションで自己採点8点に対し6点）。
自己採点が甘くなる傾向は、この時点で観測されていたことになる。
しかし 005 以降は独立採点を行っておらず、この補正は効いていない。

### 受賞水準という目標と、評価方法が対応していない

UI_GUIDELINES は受賞水準を目標にしたが、比較対象となる参照サイトや、各点数が何を意味するかの基準（アンカー）を定めていなかった。
比較対象がない採点では、「受賞サイトと並べて見劣りしない」という合格条件を確かめようがない。

### レビュー結果が Issue に戻っていない

コードレビューの要対応1件（`prefers-reduced-motion` でトランジションが止まらない）は、Issue になっていない。
フローは「レビューを作成する」で終わっており、指摘を修正するまでの工程がない。

この指摘はガイドラインに明記された要件の違反であり、本来は `design:audit` で検知できてよい種類のものである。
axe は reduced-motion 時の動きを検査しないため、機械チェックの網から漏れた。

### 異常系のカバレッジが低い

全体の行カバレッジは高いが、異常系を扱うファイルは低い。

| ファイル | 行カバレッジ | 未検証の内容（推定） |
|---|---|---|
| `src/middleware/error.tsx` | 54.54% | 500／503 の共通エラーページへの変換 |
| `src/routes/dev.tsx` | 66.66% | 開発用ルートの一部 |
| `src/middleware/auth.ts` | 80% | リモート JWKS の生成（テストではローカル JWKS を注入するため） |

Test Strategy が重点リスクに挙げた fail closed の経路のうち、JWKS の取得失敗と D1 の上限超過（503）は自動テストで検証されていない。
平均値の目標（80%）だけを見ると、この偏りは見えない。

### 人の作業を含む Issue がフローの末尾に残った

015（本番デプロイ）は、Cloudflare Access の設定などアカウント操作を含むため、`doing` のまま止まっている。
自動で進む Issue の列の中に、人の作業が必須の Issue が混ざっていると、フロー全体の完了が人の空き時間に左右される。

### ドキュメントとスキルの細かな不整合

- スキルは `docs/PROJECT_OVERVIEW.md` を前提にしているが、実際の一次ドキュメントは `spec/CONCEPT.md` で、毎回の指示で読み替えている。
- documentation-planning の候補に UI の方針がなく、UI_GUIDELINES は Issue 作成後に追加した。
- レポートの置き場所が決まっておらず、README の TODO にもドキュメント階層の整理（D1／D2／D3）が残っている。
- CLAUDE.md は「一次ドキュメントは明示的な指示があるまで修正しない」としているが、`spec/CONCEPT.md` は 016 と 018 で更新された。指示に基づく更新であれば問題ないが、その判断の記録は Issue に残っていない。
- CSS は予算 40KB に対して 38.8KB（約97%）で、以後の修正で超えやすい。

### コードレビューの単位が大きい

`/code-review` は Pull Request を前提とするが、Issue のブランチはローカルで `main` にマージしたため、PR 単位のレビューが使えなかった。
レビューは21件の Issue をマージした後に一度だけ静的に行われ、テストの実行も含まれていない。
Issue ごとにレビューしていれば、reduced-motion の不一致は 004b の時点で見つかった可能性がある。

## 改善案

| 課題 | 改善案 | 反映先 |
|---|---|---|
| 導線の問題が実装後に見つかる | 実装前に、主要な操作（コミュニティを作る、スレッドを立てる、返信する）の画面遷移とワイヤーフレームを作り、人が確認する時点を設ける | documentation-planning の候補に「UX フロー／ワイヤー」を追加。UI_GUIDELINES に操作シナリオの節 |
| 導線がセルフチェックで評価されない | 画面単位の採点に加え、操作シナリオを Playwright でたどり、手数と迷う箇所を評価する軸を足す | UI_GUIDELINES §9 |
| 自己採点の張り付き | 合格を点数の閾値でなく「前ラウンドからの改善点が残っていない」と「独立採点との差が1点以内」で判定する。点数ごとの基準（アンカー）と参照サイトを定める | UI_GUIDELINES §9 |
| 独立採点が使われなくなる | 独立採点を任意でなく必須にし、各 Issue の DoD に入れる | issues/README の共通 DoD |
| レビュー結果が放置される | レビューの指摘を Issue に変換するスキルを作る（要対応は必ず Issue 化、参考は判断を記録） | 新規スキル（例：review-to-issues） |
| レビューの単位が大きい | Issue ごとに PR を作り `/code-review` を通すか、ローカル差分を対象にレビューするスキルを用意する | issue-planning、実装手順 |
| 異常系の未検証 | カバレッジ目標を全体平均だけでなく、`middleware/` などリスクの高いファイルにも設定する。500／503 と JWKS 取得失敗のテストを追加する | TEST_STRATEGY §7 |
| 機械チェックの穴 | reduced-motion をエミュレートした状態で、`transform` のトランジションが残っていないかを検査する | `scripts/design/audit` |
| 人の作業の混在 | 人の作業が必要な Issue に印（例：`requires: human`）を付け、自動実行の対象から外す | create-local-issue、issue-planning |
| スキルとの不整合 | 一次ドキュメントのパスを設定として持たせる。CLAUDE.md に、一次ドキュメントを更新したときの記録方法を書く | 各スキル、CLAUDE.md |

## 次に行うとよいこと

優先度の高い順に挙げる。

1. **コードレビューの指摘を Issue 化して直す。** 要対応1件と、文言の不揃い（参考2）、Architecture の記述（参考4、5）を対象にする。「レビュー結果を Issue に戻す」工程を試す最初の題材になる。
2. **015 のデプロイを人の作業として完了させる。** 手動チェックリストで、Access の保護と本番の JWKS 取得を確認する。自動テストで検証していない経路なので、ここで初めて確かめられる。
3. **異常系のテストを追加する。** 500／503 のエラーページと、JWKS の取得失敗が 403 になることを検証する。
4. **スキルを改修する。** 上の改善案のうち、documentation-planning の候補追加、review-to-issues の新設、人の作業の印の3つから着手するとよい。
5. **ドキュメントの階層を整理する。** README の TODO（D1：一次、D2：二次、D3：派生物）に合わせ、レポートの置き場所も決める。
6. **フロー2を、改善後のフローで実施して比較する。**
   - スレッド内のツリー（返信のネスト）は、概念設計で「ネストなし」と決めた事項を覆す変更になる。一次ドキュメントの変更が下流のドキュメントと Issue にどう波及するかを試す題材として適している。
   - 検索は、D1 の無料枠（行読み取り数）と相性を確認する必要がある。全文検索を使う場合は、Architecture の段階で方式を決める。
   - フロー1と比べられるよう、人が介入した回数とその理由、Issue ごとの所要時間を記録する。今回はこの記録がなく、「人の確認をどれだけ減らせたか」を数値で示せなかった。
