# 一次ドキュメントと実装の乖離に関する調査（2026-10-14）

## 対象と方法

| 項目 | 内容 |
|---|---|
| 問い | 一次ドキュメント（`spec/CONCEPT.md`）から実装までの流れのどこで情報が落ち、乖離が生まれるか。その乖離に気づけるか |
| 対象フロー | 観点1：初回フロー（CONCEPT → docs → 計画 → Issue → 実装）。観点2：変更フロー（ドキュメント Issue → 実装 Issue。016〜021） |
| 根拠 | `spec/CONCEPT.md` とその変更履歴、`docs/` の各文書、`issues/`、`src/`、`test/`、`design/rounds/`、`docs/reports/2026-10-14-code-review.md` |
| 方法 | 各段階の受け渡しで、上流の記述が下流でどう扱われたかを突き合わせた。テストとビルドは実行していない |

`spec/CONCEPT.md` は CLAUDE.md の方針に従い、変更していない。

## 結論

情報が落ちる箇所は主に3つある。

1. **CONCEPT と Requirements の境界**：CONCEPT の記述には識別子がなく、Requirements の要件がどの記述に由来するかを追えない。Requirements で下した決定（削除条件の解釈、表示名など）も CONCEPT に戻っていない。
2. **実装から文書への逆流がない**：デザインのセルフチェックの中で追加された要素（ホーム欄外のコミュニティ索引など）が、どの文書にも記載されていない。
3. **変更の波及の判断が人（エージェント）の列挙に依存する**：変更フローのドキュメント Issue は、更新する文書と節を Issue 作成時に列挙する。列挙から漏れた箇所（Architecture の構成図、ホームの空状態の文言）は古いまま残った。

乖離に気づけない理由は、各段階の検証が直近の上流文書としか比較していないことにある。
Issue の受け入れ条件は Issue と、コードレビューは主に Requirements と Architecture と比較した。
各段階で局所的に整合していても、その積み重ねが CONCEPT と整合している保証にはならない。
CONCEPT と実装を直接突き合わせる工程がないため、CONCEPT の文言と実装の食い違いはレビューでも検出されなかった。

## フローと追跡の仕組み

```
CONCEPT ──①──▶ REQUIREMENTS ──②──▶ ARCHITECTURE / TEST_STRATEGY / UI_GUIDELINES
                                          │
                                          ③
                                          ▼
                     IMPLEMENTATION_PLAN（W） ──④──▶ Issue ──⑤──▶ コード／テスト ──⑥──▶ レビュー
```

| 受け渡し | 追跡の仕組み | 評価 |
|---|---|---|
| ① CONCEPT → REQ | DOCUMENTATION_PLAN §6 で、CONCEPT の未決事項の決定先だけを対応づけている | **弱い**。決定事項と機能の記述には識別子も対応表もない |
| ② REQ → ARCH ほか | FR ID。ARCH §11 と TEST_STRATEGY §5 に対応表がある | 強い |
| ③④ docs → 計画 → Issue | 計画は W ID と FR ID を、Issue は W ID と文書の節を参照する | 強い |
| ⑤ Issue → コード／テスト | Issue の受け入れ条件のチェックボックス | **中程度**。テストに FR ID がなく、要件からテストへの対応を機械的に確かめられない |
| ⑥ レビュー | 文書との静的な突き合わせ | **中程度**。基準に CONCEPT を挙げているが、実質は REQ と ARCH との比較になっている |

## 観点1：初回フローで見つかった乖離

### CONCEPT と Requirements の食い違い

| # | CONCEPT の記述 | 下流での扱い | 種類 |
|---|---|---|---|
| 1 | §8「スレッドは投稿が残っていれば削除不可」 | FR-T-7「返信がない場合に限り削除でき、本文も削除する」。本文を子要素と見なさない | 解釈による変更。文言どおりに読むと、本文が常に残るためスレッドは削除できない |
| 2 | §8 の表で投稿の削除は「○」 | FR-P-5「本文は単独では削除できない」 | 下流で追加された制約 |
| 3 | §12 未決事項（最初の投稿の扱い、表示名、SSR／SPA、スパム対策） | REQ と ARCH で4件とも決定済み | 一次ドキュメントが古いまま。未決として残っている |

1 と 2 は、CONCEPT §12 で Requirements に委ねた事項の決定であり、決定そのものは妥当と考えられる。
問題は、決定が CONCEPT に戻っていないことである。
CONCEPT だけを読む人（または一次ドキュメントを基準にするエージェント）は、文言どおりの仕様を正しいと判断する。
コードレビューは CONCEPT を基準に含めていたが、この食い違いを指摘していない。

### 実装から生まれ、文書にない要素

デザインのセルフチェック（`design/rounds/06`、`13`）の中で、次の要素が追加された。

| 要素 | 実装箇所 | 文書での記載 |
|---|---|---|
| ホーム欄外のコミュニティ索引（全コミュニティのリンク） | `src/views/pages/home.tsx` | REQ、ARCH、UI_GUIDELINES §4.2 のいずれにもない |
| コミュニティページとスレッドページの欄外注記（投稿数、最終投稿など） | `MarginNote`（`communities.tsx`、`thread.tsx`） | UI_GUIDELINES §5 の共通部品一覧にない |
| ホームの先頭行を一段大きく組む | `thread-list--first` | なし |

欄外の索引は、ホームで全コミュニティを読む追加クエリを伴う。
コードレビューは読み取り量の見積もりとのずれ（参考5）としてだけ扱い、「文書にない機能」としては指摘していない。
デザインの改善ループは見た目の改善として要素を足せるが、その結果を文書に戻す規則がない。
ここが、実装を起点とする乖離（下流から上流へのずれ）の入口になっている。

### 受け入れ条件の二重管理

REQUIREMENTS §10 の受け入れ条件31項目は、すべて未チェック（`- [ ]`）のままである。
完了の判定は各 Issue の受け入れ条件で行われ、REQ の受け入れ条件と実装を直接照合した記録がない。
014 で TEST_STRATEGY §5 の対応表との突き合わせは行われているが、照合の結果が REQ 側に残っていない。

また、テストには FR ID が含まれていない（`test/` に `FR-` の出現なし）。
要件からテストへの対応は TEST_STRATEGY §5 の表（ファイル名の単位）に頼っており、要件を変えたときに影響するテストを機械的に特定できない。

## 観点2：変更フローで見つかった点

### うまく機能していた点

- 016 と 018 は、CONCEPT の変更を Out of scope に置いたうえで、ユーザーに確認し、その決定（CONCEPT §7 を更新する）を Issue に記録した。CLAUDE.md の方針と整合している。
- 018 は「019 への影響」として、変更されるテストとヘルパーを列挙した。ドキュメント Issue が実装 Issue の仕様書として働いている。
- 020 は、UI_GUIDELINES §7「フォームはすべてラベル付き」との衝突を実装の前に文書で解消し、REQ を変更しない判断も理由付きで記録した。

### 乖離が生まれた点

| # | 内容 | 原因 |
|---|---|---|
| 1 | ホームの空状態の文言「コミュニティを開いて、最初のスレッドを立てましょう。」が、019 以降の導線（ヘッダーの「投稿する」）と合っていない。コミュニティページの文言は更新済み | 018 の Scope が変更対象の画面（作成ページ、コミュニティページ）を列挙した一方、導線の変更が他画面の文言に波及することを洗い出していない |
| 2 | ARCH §3 の構成図が「4画面」のまま（現在は作成ページを含めて6画面） | 016 は ARCH §5 の「4画面のまま」の記述を更新対象にしたが、§3 の同じ記述は列挙していない |
| 3 | CONCEPT §12 の未決事項は、016・018 で CONCEPT を更新した際にも古いまま | ドキュメント Issue は、変更に関係する節だけを編集対象にする。一次ドキュメント全体の整合は確認対象になっていない |

いずれも、ドキュメント Issue の Scope に「どの文書のどの節を直すか」を列挙する方式から生じている。
列挙は Issue を書く時点の判断であり、全文検索などで影響範囲を網羅的に洗い出す手順がない。
実装 Issue の受け入れ条件はドキュメント Issue の決定事項から作られるため、列挙から漏れた箇所は実装でも検証されない。

### 変更が CONCEPT と整合するかの確認

016〜021 の変更は、いずれもユーザーの指示（デザイン修正）を起点に、REQ と UI_GUIDELINES の層から入っている。
今回の変更は画面構成の範囲で、CONCEPT の目的（発見と一望）や決定事項とは矛盾していない。
ただし、ドキュメント Issue の手順に「CONCEPT の目的、決定事項、非スコープに反しないか」を確認する項目はなく、整合は結果としてそうなっていたにすぎない。
フロー2で予定している「スレッド内のツリー」は CONCEPT の決定事項（ネストなし）と非スコープを覆す変更であり、この確認がないと、下流だけを変えて CONCEPT と矛盾したまま進む可能性がある。

## 乖離に気づけない構造的な原因

1. **一次ドキュメントに識別子がない。** 要件の由来を追えず、CONCEPT のどの記述が実装されていないか（または変えられたか）を機械的に確認できない。
2. **下流から上流へ戻す工程がない。** Requirements での決定、実装中の追加要素が、一次ドキュメントや上位の文書に戻らない。
3. **検証が隣接する文書との比較に限られる。** 局所的な整合の積み重ねでは、CONCEPT との整合を保証できない。
4. **受け入れ条件が REQ と Issue で二重に存在し、REQ 側が使われていない。**
5. **テストに要件 ID がない。** 要件とテストの対応を自動で確かめられない。
6. **変更の影響範囲を列挙に頼っている。** 用語、画面名、ルート、文言を検索して洗い出す手順がない。
7. **作成者と検証者が同じ文脈を共有している。** 同じエージェント（同じ前提）が Issue を書き、実装し、チェックする。

## 対策

### 観点1（初回フロー）

| 対策 | 内容 | 効く原因 |
|---|---|---|
| CONCEPT に識別子を振る | 決定事項、機能スコープ、非スコープの各行に `C-01` などの ID を付ける。REQ の各要件に「由来：C-xx」を書く | 1 |
| トレースの機械チェック | スクリプトで「すべての C-ID が REQ から参照されている」「すべての FR ID が少なくとも1つのテスト名に含まれる」を確認し、DoD に入れる | 1、5 |
| テスト名に FR ID を入れる | `it("FR-T-7: 返信があるスレッドは削除できない", …)` のように書く | 5 |
| 決定の逆流 | 下流で決めた事項は決定ログに記録し、CONCEPT の該当箇所（未決事項、関連する決定事項）の更新要否をユーザーに確認する Issue を作る | 2 |
| 実装起点の要素の記録 | デザインのループで画面要素を追加した場合は、UI_GUIDELINES（必要なら REQ）への記載を合格条件にする。レビューの観点に「文書にない機能」を加える | 2 |
| REQ の受け入れ条件で最終照合 | 最後の品質 Issue（014 相当）で、REQ §10 を1項目ずつ実装と照合してチェックし、結果を REQ に残す | 4 |
| 一次ドキュメント準拠レビュー | 実装の文脈を持たない別のエージェントに、CONCEPT と実装（画面とコード）だけを渡して突き合わせさせる。REQ を介さないことで、中間の解釈を検証できる | 3、7 |

### 観点2（変更フロー）

ドキュメント Issue のテンプレートに、次の手順を加える。

1. **CONCEPT との整合確認**：変更が CONCEPT の目的、決定事項、非スコープ（C-ID）に反しないかを確認し、反する場合は CONCEPT の変更をユーザーに確認する。
2. **影響範囲の洗い出し**：変更する用語、画面名、ルート、文言を `docs/`、`spec/`、`src/`、`test/` で全文検索し、ヒットした箇所と対応（更新する／しない理由）を Issue に記録する。
3. **一次ドキュメント全体の再確認**：CONCEPT を更新する場合は、未決事項など変更対象以外の節も古くなっていないかを確認する。
4. **実装 Issue への転記**：ドキュメント Issue の決定事項と、2 で洗い出した箇所を、実装 Issue の受け入れ条件に1項目ずつ転記する。

実装 Issue の完了時には、ドキュメント Issue の決定事項を1項目ずつ実装と照合し、照合結果を Issue に残す。
画面の文言は、UI_GUIDELINES に文言の一覧を持たせると、導線の変更で更新すべき文言を検索で見つけやすくなる。
