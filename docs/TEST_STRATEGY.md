# テスト方針（Test Strategy）

`docs/REQUIREMENTS.md` の要件と、`docs/ARCHITECTURE.md` で特定した主要リスクを、どのテストで検証するかを定める。実装は TDD（red → green）で進め、テストは本書で合意したシームでのみ書く。

## 1. 方針

- **振る舞いを公開境界で検証する。** 内部の協調者（services、repositories）はモックしない。
- **実物を安く使う。** D1 はローカルの実体（Miniflare）を使い、本番と同じマイグレーションを適用する。
- **認証もテストで本番の経路を通す。** テスト用の鍵で署名した JWT を送り、Access の JWT 検証を毎回実行する。
- **期待値は仕様から書く。** 実装と同じ計算で期待値を作らない。たとえば並び順は、具体的な作成順と時刻から期待する順序を固定値で書く。
- **ブラウザでしか確かめられないものは手動で確認する。** E2E の自動テストは作らない。
  - 見た目とアクセシビリティは、`docs/UI_GUIDELINES.md` §9〜10 のデザイン確認（Playwright によるスクリーンショットと axe）で確認する。これは振る舞いを検証するテストではなく、`npm test` には含めない。

## 2. シーム（テストを書く境界）

| # | シーム | 対象 | 入力 → 観測 |
|---|---|---|---|
| S1 | **HTTP 境界** | Worker 全体（ミドルウェア → routes → services → repositories → ローカル D1 → views） | HTTP リクエスト → ステータス、`Location` ヘッダー、HTML の内容 |
| S2 | **lib の純粋関数** | 入力検証（trim 後の文字数）、表示名の導出、UTC → JST の変換、コミュニティ色相の導出 | 引数 → 戻り値 |

- services / repositories 単体のテストと、そのためのテストダブルは作らない。削除条件・派生値・本人確認は、S1 で HTTP の応答として観測する。
- S2 は、境界値を S1 で網羅するとケースが多くなりすぎる関数に限る。S1 と同じ観点を重複して書かない。
- DB を直接読んで結果を確かめない（副経路での検証をしない）。データの作成も確認も HTTP 経由で行う。

## 3. ツールと実行環境

| 用途 | ツール | 備考 |
|---|---|---|
| テストランナー | Vitest | |
| Workers ランタイムでの実行 | `@cloudflare/vitest-plugin` | 2026-08 に `@cloudflare/vitest-pool-workers` から改名された v1。設定は `cloudflareTest({ wrangler: { configPath: "./wrangler.jsonc" } })` |
| カバレッジ | `@vitest/coverage-istanbul` | Workers ランタイムでは V8 方式が使えないため Istanbul を使う |
| 型チェック | `tsc --noEmit` | 合格条件に含める |
| JWT の生成 | `jose` | 本番の検証と同じライブラリで、テスト用の鍵ペアを生成して署名する |

対応する Vitest のバージョンは、導入時に `@cloudflare/vitest-plugin` のドキュメントで確認する。

### 3.1 D1

- `readD1Migrations("./migrations")` で読み込んだマイグレーションを、テスト専用のバインディング `TEST_MIGRATIONS` として渡す。`setupFiles` で `applyD1Migrations` を実行する。
- ストレージはテストファイル単位で分離され、ファイルの終了時に書き込みが取り消される。同じファイル内のテストは DB を共有する。
  - 各テストは、自分が作ったデータ（一意な名前など）だけを前提にする。
  - 全体の件数や並び順に依存するテスト（ホームのページング、横断の並び順）は、専用のファイルに分ける。
- ストレージ操作とレスポンスボディの読み取りは、すべて `await` する（分離ストレージの既知の制約）。

### 3.2 依存の注入（時刻と JWKS）

アプリは `createApp({ now, jwks })` のようなファクトリで生成する（ARCHITECTURE §3）。

| 依存 | 本番 | テスト |
|---|---|---|
| 現在時刻 `now` | 実時刻 | 手動で進める時計。並び順・最終投稿日時・「編集済み」のテストで、作成時刻を明示的に決める |
| JWKS `jwks` | `createRemoteJWKSet(TEAM_DOMAIN + "/cdn-cgi/access/certs")` | テスト用の公開鍵による `createLocalJWKSet` |

同じミリ秒に複数のリクエストが処理されて、並び順が不安定になるのを防ぐため、時刻は注入する。

### 3.3 テスト用ヘルパー

| ヘルパー | 役割 |
|---|---|
| `tokenFor(email, overrides?)` | テスト用の鍵で JWT を署名する。`iss`・`aud`・`exp`・`email` を上書きでき、検証失敗のケースも作れる |
| `as(email)` | 指定ユーザーの JWT と自ホストの `Origin` を付けて、GET / POST（フォーム）を送る |
| `html(res)` | レスポンスから、テキスト・要素・フォームの有無・リンクを抽出する |
| `createCommunity` / `createThread` / `reply` | HTTP 経由でデータを作り、作成された ID を `Location` から返す |

テスト内での HTML の確認は、ヘルパー経由で「何が表示されているか」に限る。CSS クラスや DOM の細かな構造には依存しない。

### 3.4 ディレクトリ構成（案）

```
test/
  setup/apply-migrations.ts
  helpers/            # app 生成（時計・JWKS 注入）、tokenFor、as、html、データ作成
  lib/                # S2：validation / display-name / time / community-hue
  http/               # S1
    auth.test.ts
    communities.test.ts
    threads.test.ts
    posts.test.ts
    listing-home.test.ts       # 全体件数・並び順に依存（専用ファイル）
    listing-community.test.ts
    security.test.ts           # XSS、Origin、他人のリソース
    errors.test.ts             # 404 など
    styleguide.test.ts         # /_styleguide が dev 以外で 404
```

## 4. 重点的に検証するリスク

ARCHITECTURE で特定した、壊れると要件違反に直結する箇所。すべて S1 で検証する。

| リスク | 検証内容 |
|---|---|
| 認証の fail closed | JWT なし、署名不正、`aud` 不一致、`iss` 不一致、期限切れ、対象外ドメインのメール → すべて 403。`AUTH_MODE` 未設定時は JWT が必須 |
| 開発用認証 | `AUTH_MODE=dev` のときだけ `DEV_USER_EMAIL` として扱われる |
| 本人確認 | 他人のコミュニティ・スレッド・投稿への修正・削除の POST が 403 になり、その後の GET で内容が変わっていない。修正・削除の操作が他人には表示されない |
| 削除条件 | スレッドがあるコミュニティ、返信があるスレッドの削除が 409 になり、親も子も残る。本文には削除操作がなく、本文の削除 POST は拒否される |
| 派生値（ADR-3） | 返信の作成で投稿数が増え、スレッドが一覧の先頭に移動する。最新の返信を削除すると、投稿数と最終投稿日時が戻り、並び順に反映される。投稿の修正では並び順が変わらない |
| CSRF | `Origin` が自ホストでない POST は 403 |
| XSS | `<script>` を含む入力が、エスケープされた文字列として表示される |
| 一意性 | 大小文字だけが異なる名前、前後に空白がある同名は重複として 409 になる（作成・修正とも） |

## 5. 受け入れ条件との対応

`docs/REQUIREMENTS.md` §10 の各項目を検証する場所。

| 受け入れ条件 | 検証 |
|---|---|
| **認証・権限** | |
| Access の認証情報を持たないリクエストは拒否 | S1 `auth` |
| 投稿者名が `@` より前で表示 | S2 `display-name`、S1 `posts`（表示の確認） |
| 他人のリソースに修正・削除操作が表示されない | S1 `security` |
| 他人のリソースへの修正・削除リクエストが拒否され、データが変わらない | S1 `security` |
| **コミュニティ** | |
| 作成とコミュニティページへの移動 | S1 `communities` |
| 同名で作成・修正できない | S1 `communities` |
| 名前・説明の入力制約 | S2 `validation`（境界値）、S1 `communities`（400 と再表示の代表ケース） |
| 名前順の一覧 | S1 `communities` |
| スレッドの有無による削除可否と遷移 | S1 `communities` |
| **スレッド** | |
| 作成と遷移、本文が先頭 | S1 `threads` |
| タイトル・本文の入力制約 | S2 `validation`、S1 `threads`（代表ケース） |
| ホームは横断、コミュニティページは該当のみ | S1 `listing-home`、`listing-community` |
| 最終投稿日時の順。返信で先頭へ | S1 `listing-home` |
| 最新の返信の削除で最終投稿日時が戻る | S1 `listing-home` |
| 修正では並び順が変わらない | S1 `listing-home` |
| 21件以上で20件ずつのページ | S1 `listing-home`、`listing-community` |
| 一覧の各行の表示項目 | S1 `listing-home`、`listing-community` |
| タイトル修正で「編集済み」 | S1 `threads` |
| 返信の有無による削除可否と遷移 | S1 `threads` |
| **投稿** | |
| 返信が末尾に表示 | S1 `posts` |
| 古い順、ネストなし | S1 `posts` |
| 修正で「編集済み」 | S1 `posts` |
| 返信は削除可、本文に削除操作なし | S1 `posts` |
| HTML が文字列として表示、改行保持 | S1 `security`（エスケープ）、手動（改行の見た目） |
| **表示** | |
| JST の `YYYY-MM-DD HH:mm` | S2 `time`（日付をまたぐ境界）、S1（表示の代表ケース） |
| 存在しない URL で見つからない旨 | S1 `errors` |
| スマホ幅で閲覧・投稿できる | 手動 |

## 6. 手動テスト（デプロイ後）

自動テストで検証できない項目を、デプロイ後にチェックリストで確認する。

- [ ] 対象ドメインの Google アカウントでログインし、4画面を閲覧・投稿できる
- [ ] 対象外ドメインの Google アカウントではログインできない
- [ ] workers.dev のプレビュー URL が無効になっている
- [ ] 削除時に確認ダイアログが表示され、キャンセルすると削除されない
- [ ] 編集フォーム（`<details>`）が JS なしで開閉できる
- [ ] 投稿本文の改行がそのまま表示される
- [ ] スマートフォンの画面幅で、各画面の閲覧と投稿ができる
- [ ] 本番の JWKS 取得で JWT 検証が通る（ログインできることで確認）
- [ ] Cloudflare ダッシュボードで、CPU 時間が 10 ms 以内に収まっている

## 7. 合格基準と実行

| 項目 | 基準 |
|---|---|
| テスト | 全件成功 |
| カバレッジ | `src/` の行カバレッジ 80% 以上（Istanbul、下回ると失敗） |
| 型チェック | `tsc --noEmit` がエラーなし |
| 受け入れ条件 | §5 のすべての項目に、対応する自動テストまたは手動チェックがある |

- CI は設けない。コミット前にローカルで test・coverage・typecheck を全件実行する。
- npm スクリプト名（例：`test`、`test:coverage`、`typecheck`）は実装計画で決め、`CLAUDE.md` の「コマンド」節に記載する。
- カバレッジの数値を満たすためだけのテストは書かない。不足する場合は、§2 のシームで未検証の振る舞いがないかを先に確認する。

## 8. 未検証のリスク

自動テストでは検証せず、把握したうえで受け入れるもの。

| リスク | 扱い |
|---|---|
| 本番の JWKS 取得（`createRemoteJWKSet`）| テストではローカル JWKS を注入するため経路が異なる。手動テストのログインで確認する |
| Access の設定ミス（ポリシー、AUD） | アプリの外の設定。手動テストで確認する |
| CPU 時間 10 ms の制限 | ローカルでは再現しない。デプロイ後にダッシュボードで確認し、超過すれば対策を検討する |
| ローカル D1 と本番 D1 の挙動差 | 同じマイグレーションを使うことで差を小さくする。外部キーの既定動作はマイグレーション作成時に確認する |
| 同時実行時の競合（削除と返信が同時に起きる場合） | 逐次のテストで、DELETE 文の条件（子要素あり → 0行）を検証することで代替する。真の並行実行は検証しない |
| フリープランの日次上限の超過 | 再現しない。数名利用の見積もり（ARCHITECTURE §4.5）で受け入れる |
