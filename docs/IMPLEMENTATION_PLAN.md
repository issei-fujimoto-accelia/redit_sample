# 実装計画（Implementation Plan）

`spec/CONCEPT.md`（Project Overview）と `docs/REQUIREMENTS.md`・`docs/ARCHITECTURE.md`・`docs/TEST_STRATEGY.md`・`docs/UI_GUIDELINES.md` を基に、実装対象・依存関係・実装順序・テスト方針を定める。
本書は issue-planning で Issue へ分割する際の入力とする。コードの細かな実装手順は書かない。

## 1. 前提と進め方

- 実装は TDD（red → green）で進める。各作業は次の順で進める。
  1. failing test（合意済みシームでのみ書く）
  2. minimal implementation
  3. test pass
  4. refactor（レビュー段階で行い、red → green のループには含めない）
- テストのシームは `TEST_STRATEGY.md` §2 で合意済みの2つに限る。
  - **S1：HTTP 境界**（Worker 全体＋ローカル D1。ステータス・`Location`・HTML を観測）
  - **S2：lib の純粋関数**（入力検証・表示名導出・UTC→JST 変換）
- services / repositories 単体のテスト、テストダブル、DB を直接読む検証は書かない。
- **垂直スライス**で進める。1つの振る舞いについて「テスト1件 → 最小実装」を繰り返し、全テストを先に書かない。
- 各作業の完了条件には、共通して次を含める（以下「共通 DoD」）。
  - 追加したテストを含め `npm test` が全件成功する。
  - `npm run typecheck` がエラーなし。
  - 対応する要件 ID・受け入れ条件がテストで検証されている。
  - 画面を追加・変更する作業（W4b 以降）は、`UI_GUIDELINES.md` §9 のセルフチェックで合格している（対象はその作業で触れた画面と状態）。

## 3. 作業一覧

作業はマイルストーン（M0〜M6）ごとにまとめる。ID は Issue 分割時の参照に使う。

### M0：基盤

#### W1 プロジェクト雛形とテスト基盤

- **目的**：Worker を Vitest（Workers ランタイム）でテストでき、ローカル D1 にマイグレーションが適用される状態にする。
- **対象**：`package.json`、`tsconfig.json`、`wrangler.jsonc`（D1 binding `DB`、`workers_dev: true`、`preview_urls: false`）、`vitest.config.ts`（`@cloudflare/vitest-plugin` の `cloudflareTest`、`TEST_MIGRATIONS`、Istanbul）、`test/setup/apply-migrations.ts`、`migrations/0001_init.sql`、`src/index.ts`（`createApp({ now, jwks })` の骨格）、`.dev.vars.example`、`.gitignore`、`CLAUDE.md` のコマンド節。
- **テスト（S1・tracer）**：`createApp` で生成したアプリに `GET /` を送り、200 とレイアウト（ホーム・コミュニティ一覧へのリンク）が返る。※認証は W3 で追加し、このテストは W3 で `as(email)` 経由に置き換える。
- **確認事項**：
  - `@cloudflare/vitest-plugin` に対応する Vitest のバージョン。
  - D1 で外部キー制約が有効か（`PRAGMA foreign_keys`）。無効なら ARCHITECTURE §4.1 の前提を見直す。
- **完了条件**：共通 DoD。`npm run test:coverage` が動作する。`wrangler dev` でローカル起動できる。

#### W2 lib の純粋関数（S2）

- **目的**：境界値の多い純粋関数を先に固める。W1 と並行可能。
- **対象**：`src/lib/validation.ts`、`src/lib/display-name.ts`、`src/lib/time.ts`。
- **テスト（S2）**：
  - validation：trim 後の文字数で判定。空・空白のみ・上限ちょうど・上限＋1（名前50／説明500・任意／タイトル200／本文10,000）。
  - display-name：`alice@example.com` → `alice`。
  - time：UTC → JST `YYYY-MM-DD HH:mm`。UTC 15:00 が JST 翌日 00:00 になる日付またぎ。
- **要件**：REQ §6.2、FR-C-2、FR-C-3。
- **完了条件**：共通 DoD。

#### W3 認証ミドルウェアとテストヘルパー

- **目的**：全リクエストを Access JWT で検証し、ユーザーを `c.var.user` に設定する（fail closed）。
- **対象**：`src/middleware/auth.ts`、テストヘルパー（`tokenFor`、`as`、`html`、アプリ生成時の時計・ローカル JWKS 注入）。
- **テスト（S1 `auth.test.ts`）**：
  - 有効な JWT → 200。
  - JWT なし／署名不正／`aud` 不一致／`iss` 不一致／期限切れ／対象外ドメインのメール → 403。
  - `AUTH_MODE` 未設定時は JWT 必須。`AUTH_MODE=dev` のときだけ `DEV_USER_EMAIL` として扱われる。
- **要件**：FR-C-1、ARCH §7.2〜7.3、ADR-6。
- **依存**：W1。
- **完了条件**：共通 DoD。W1 の tracer テストが `as(email)` 経由で成功する。

#### W4 共通ミドルウェア・レイアウト・エラーページ

- **目的**：CSRF 対策、例外処理、共通レイアウトを用意し、以降の画面作業の土台にする。
- **対象**：`src/middleware/origin.ts`（Hono `csrf`）、`src/middleware/error.ts`、`src/views/Layout`、共通エラーページ（403／404／500／503）。
- **テスト（S1 `security.test.ts`、`errors.test.ts`）**：
  - `Origin` が自ホストでない POST → 403。
  - 未定義のパス → 404 と見つからない旨の表示。
- **要件**：FR-C-7（一部）、ARCH §5.1、§7.4。
- **依存**：W3。
- **完了条件**：共通 DoD。

#### W4b UI 基盤とデザインシステム

- **目的**：各画面の作業に入る前に、見た目の方針・デザイントークン・共通部品をそろえ、品質のセルフチェックの仕組みを用意する（`UI_GUIDELINES.md`）。
- **対象**：アプリ名・ワードマーク・欧文書体の決定（ユーザーと相談）、`wrangler.jsonc` の `assets`、CSS（`@layer`、トークン、ライト／ダーク）、`src/views/components/`（UI_GUIDELINES §5）、Layout・エラーページの仕上げ、`src/lib/community-hue.ts`、`GET /_styleguide`（`AUTH_MODE=dev` のみ）、`scripts/design/`（seed・capture・audit）。
- **テスト**：
  - S2 `community-hue`：同じ ID に同じ色相、0〜359 の整数、隣り合う ID が近い色相にならない。
  - S1 `styleguide`：`AUTH_MODE` が `dev` 以外で `/_styleguide` → 404、`dev` で 200。
- **要件**：NFR-1、UI_GUIDELINES 全体。
- **依存**：W4。
- **完了条件**：共通 DoD。スタイルガイドページとエラーページで UI_GUIDELINES §9 の合格基準を満たし、ユーザーが承認している。

### M1：コミュニティ

#### W5 コミュニティの作成と一覧

- **対象**：`GET /c`、`POST /c`、`GET /c/:id`（名前・説明と空のスレッド一覧）、関連する routes / services / repositories / views。
- **テスト（S1 `communities.test.ts`）**：
  - 作成すると 303 → `/c/:id`、コミュニティページに名前・説明・作成者の表示名が出る。
  - 一覧が名前順に並ぶ。
  - 名前が空・51文字 → 400 で入力値とエラー付き再描画（代表ケース）。
  - 同名、大小文字違い、前後空白付きの同名 → 409。
  - 存在しない `/c/:id` → 404。
- **要件**：FR-CM-1、FR-CM-2、REQ §6.2、FR-C-7。
- **依存**：W2、W4b。

#### W6 コミュニティの修正と削除（スレッドなし）

- **対象**：`POST /c/:id/edit`、`POST /c/:id/delete`、削除確認の `confirm`、`<details>` の編集フォーム。
- **テスト（S1 `communities.test.ts`、`security.test.ts`）**：
  - 作成者が名前・説明を修正できる。修正後の名前が他と重複 → 409。
  - スレッドのないコミュニティを削除 → 303 → `/c`、一覧から消える。
  - 他人には修正・削除の操作が表示されない。他人の修正・削除 POST → 403、その後の GET で内容が変わっていない。
- **要件**：FR-CM-3、FR-CM-4（スレッドなし）、FR-C-4、FR-C-5。
- **依存**：W5。

### M2：スレッド

#### W7 スレッドの作成とスレッドページ

- **対象**：`POST /c/:id/threads`（タイトル＋本文を1つの batch で INSERT）、`GET /t/:id`、コミュニティページのスレッド作成フォーム。
- **テスト（S1 `threads.test.ts`）**：
  - 作成すると 303 → `/t/:id`、タイトルと本文（先頭の投稿・作成者の表示名・JST 日時）が表示される。
  - タイトル空・201文字、本文空・10,001文字 → 400（代表ケース）。
  - 存在しないコミュニティへの作成、存在しない `/t/:id` → 404。
- **要件**：FR-T-5、FR-P-1（本文のみ）、FR-P-2、REQ §6.2。
- **依存**：W5。

#### W8 コミュニティページのスレッド一覧

- **対象**：`GET /c/:id` のスレッド一覧（`last_posted_at DESC, id DESC`、20件ページング、`?page=N`）。
- **テスト（S1 `listing-community.test.ts`）**：
  - そのコミュニティのスレッドだけが表示される。
  - 各行にタイトル、作成者、投稿数、最終投稿日時が表示される（コミュニティ名は表示しない）。
  - 作成時刻を時計で固定し、新しい順・同時刻は後に作成したものが上。
  - 21件で2ページに分かれる。不正な `page` は1扱い、範囲外は空の一覧。
- **要件**：FR-T-1〜4（コミュニティページ）。
- **依存**：W7。

#### W9 スレッドの修正と削除（返信なし）、コミュニティ削除の不可条件

- **対象**：`POST /t/:id/edit`、`POST /t/:id/delete`（本文→スレッドを条件付き DELETE の batch）、コミュニティ削除の 409。
- **テスト（S1 `threads.test.ts`、`communities.test.ts`、`security.test.ts`）**：
  - タイトルを修正すると「編集済み」が表示される。
  - 返信のないスレッドを削除 → 303 → `/c/:community_id`、本文ごと消える。
  - スレッドがあるコミュニティの削除 → 409 と理由の表示、コミュニティもスレッドも残る。
  - 他人のスレッドの修正・削除 → 403、操作非表示。
- **要件**：FR-T-6、FR-T-7（返信なし）、FR-CM-4（スレッドあり）、FR-C-4。
- **依存**：W6、W7。

- **要件**：FR-P-4、FR-P-5、FR-P-6（削除）、FR-C-4。

## 4. 依存関係と実装順序

```
W1 ──┬─▶ W3 ─▶ W4 ─▶ W4b ─▶ W5 ─┬─▶ W6 ──────────┐
     │                          │                ▼
W2 ──┴──────────────────────────┴─▶ W7 ─┬─▶ W9 ─────────┐
                                        └─▶ W8 ─▶ W10 ─▶ W11 ─┬─▶ W12
                                                              └─▶ W13 ─▶ W14 ─▶ W15
```

| 順 | 作業 | 並行可能 |
|---|---|---|
| 1 | W1、W2 | W2 は W1 と並行可（S2 は D1 不要） |
| 2 | W3 → W4 → W4b | W4b はユーザーとの相談（アプリ名・書体）とレビューを含む |
| 3 | W5 | |
| 4 | W6、W7 | W5 完了後に並行可 |
| 5 | W8、W9 | W9 は W6・W7 完了後。W8 と並行可 |
| 6 | W10 → W11 | |
| 7 | W12、W13 | W11 完了後に並行可 |
| 8 | W14 → W15 | |

順序の考え方：

1. **認証と共通処理を最初に通す。** 全テストが `as(email)` を経由するため、認証が後から入ると既存テストを書き直すことになる。続けて W4b で見た目の基盤と共通部品をそろえ、各画面が同じ部品と基準で作られるようにする。
2. **コミュニティ → スレッド → 投稿の順に積む。** データの親子関係どおりで、各スライスが前のスライスの HTTP 操作だけでテストデータを作れる。
3. **削除の「不可」条件は子要素を作れるようになってから実装する。** コミュニティ削除の 409 は W9、スレッド削除の 409 は W12 に置く。
4. **ホームの並び順は投稿の作成・削除が揃ってから実装する。** 派生値（ADR-3）の検証に返信の作成・削除が必要なため、W13 は W11 の後に置く。

## 6. リスクと対応

| リスク | 対応する作業 | 対応 |
|---|---|---|
| D1 の外部キー既定動作が想定と異なる | W1 | 最初に確認し、無効なら ARCHITECTURE を更新してから進める |
| `@cloudflare/vitest-plugin` と Vitest のバージョン不整合 | W1 | 導入時に公式ドキュメントで対応バージョンを確認する |
| 派生値（`post_count`・`last_posted_at`）の更新漏れ | W10、W11、W13 | 作成・削除・修正それぞれで一覧の表示と並び順を HTTP で検証する |
| 認証の fail open | W3 | 失敗ケースをすべて 403 で検証。`AUTH_MODE` は `.dev.vars` のみに置く |
| CPU 時間 10 ms の超過 | W15 | デプロイ後にダッシュボードで確認し、超過時に対策を検討する |
| 本番 JWKS・Access 設定の誤り | W15 | 手動チェックリスト（ログイン可否、対象外ドメインの拒否）で確認する |

## 7. Issue 分割への引き継ぎ

- 原則として **1作業（W1〜W15、W4b）＝ 1 Issue** とする。いずれも1セッションで実装・検証できる規模を想定している。W4b は後から追加した作業で、Issue 番号は 004b とする。1セッションに収まらない場合は Issue 内で2ステップに分ける。
- W1 と W2、W6 と W7、W8 と W9、W12 と W13 は並行して着手できる。
- 各 Issue の Tests には、本書の「テスト」欄をそのまま red の候補として転記する。テストは1件ずつ red → green で進める。
- W15 はコード変更が少なく、設定作業と手動確認が中心になる。
