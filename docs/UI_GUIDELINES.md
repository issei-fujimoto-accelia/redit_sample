# UI ガイドライン（UI Guidelines）

見た目の方針、デザイントークン、共通部品、品質基準とセルフチェックの手順を定める。
画面と振る舞いは `docs/REQUIREMENTS.md`、構成と制約は `docs/ARCHITECTURE.md` に従う。本書はそれらを変えず、その上に乗る見た目と品質の基準を定める。

## 1. 品質目標

### 1.1 目標

**Awwwards、Webby Awards、FWA で賞を獲れる水準**を目指す。実装者はセルフチェックを繰り返し、§9 の合格基準に達するまで品質を上げ続ける。

### 1.2 本アプリでの解釈

受賞サイトの多くは WebGL やスクロール演出を多用する。しかし本アプリは「読む・書く」ための掲示板であり、次の制約もある。

- SSR（Hono＋JSX）で、クライアント JS は削除確認のみ（ARCHITECTURE §2）
- Workers Free の CPU 時間は 10 ms／リクエスト（ARCHITECTURE §9.1）

そのため、**演出の量ではなく完成度で受賞水準に到達する**。具体的には、タイポグラフィ、余白とグリッド、配色、状態の網羅、動きの質、アクセシビリティ、速度で勝負する。

使わないもの：WebGL、スクロール連動演出、ローディング演出、自動再生の動画、カーソル追従などの装飾的 JS。

### 1.3 審査観点との対応

主要アワードの審査観点（2026-10-13 時点の一般的な理解。配点や詳細は各公式サイトで要確認）を、§9 の評価軸に対応づける。

| アワード | 主な審査観点 | 本書の評価軸 |
|---|---|---|
| Awwwards | Design / Usability / Creativity / Content | A・C・B・E |
| Webby Awards | Visual Design / Structure & Navigation / Functionality / Interactivity / Content / Overall Experience | A・C・G・D・E・全体 |
| FWA | 革新性、体験の質（審査団による選出） | B・D |

## 2. デザインコンセプト

### 2.1 コンセプト：議論の索引（Index）

雑誌や新聞の目次のような、**編集的なタイポグラフィ**で掲示板を組む。スレッド一覧を「紙面」として読ませ、見出しを拾い読みするうちに気になる議論に出会える体験を目指す。これは「発見」（ホーム）と「一望」（コミュニティページ）という本アプリの核に直結する。

| キーワード | 意味 |
|---|---|
| 編集的 | 見出し・メタ情報・本文の階層を、書体と大きさと余白だけで明快に組む |
| 静かな精度 | 装飾を足さず、揃え・行間・数字の組み・状態変化の細部で質を出す |
| 発見の手触り | コミュニティごとの色、更新のある行の存在感で、一覧に起伏をつくる |

### 2.2 シグネチャー

見た瞬間にこのアプリだとわかる要素を3つに絞り、全画面で一貫させる。

1. **コミュニティ色相**：コミュニティ ID から色相を決定的に導出し、チップ・見出しのアクセント・一覧行の印に使う。横断一覧でも出自がひと目でわかる。
2. **スレッド一覧の行**：大きく組んだタイトルと、等幅数字で揃えた投稿数・最終投稿日時。本アプリの顔となる部品として最も手をかける。
3. **ワードマーク**：「Marginalia」を Fraunces の中字（Margin）と細字（alia）で組み、左に朱の縦罫（欄外の書き込みの印）を置く。

### 2.3 避けること

- 汎用 UI キットやテンプレートそのままの見た目
- Reddit の模倣（ロゴ、配色、マスコット、レイアウトの写し）
- 意味のない装飾、影の多用、角丸の多用

## 3. デザイントークン

CSS カスタムプロパティで定義し、値の直書きを禁止する。以下は初期値で、§9 のループで調整してよい。調整した場合は本書を更新する。

### 3.1 色

色は `oklch()` で定義する。ライトとダークの両方を用意し、`prefers-color-scheme` で切り替える。

| トークン | 用途 | ライト（初期値） | ダーク（初期値） |
|---|---|---|---|
| `--color-paper` | 背景 | `oklch(98.5% 0.006 85)` | `oklch(17% 0.01 260)` |
| `--color-paper-2` | 面の区別（フォーム背景など） | `oklch(95.5% 0.008 85)` | `oklch(21% 0.012 260)` |
| `--color-ink` | 本文・見出し | `oklch(21% 0.015 260)` | `oklch(94% 0.008 85)` |
| `--color-ink-2` | メタ情報 | `oklch(45% 0.015 260)` | `oklch(76% 0.01 85)` |
| `--color-line` | 罫線 | `oklch(88% 0.008 85)` | `oklch(31% 0.012 260)` |
| `--color-line-strong` | 見出しの罫線 | `--color-ink` と同じ | 同左 |
| `--color-accent` | 主要操作、リンクのホバー | `oklch(57% 0.19 35)`（朱） | `oklch(73% 0.15 40)` |
| `--color-accent-ink` | アクセント上の文字 | `oklch(99% 0.004 85)` | `oklch(17% 0.01 260)` |
| `--color-danger` | 削除、エラー | `oklch(52% 0.2 25)` | `oklch(72% 0.16 25)` |
| `--color-danger-paper` | エラーの面 | `oklch(96% 0.025 25)` | `oklch(24% 0.05 25)` |
| `--color-focus` | フォーカスリング | `--color-accent` と同じ | 同左 |

**コミュニティ色相**：`--community-hue` に 0〜359 の数値を入れ、`oklch(L C var(--community-hue))` で使う。明度と彩度はトークンで固定し、どの色相でもコントラスト基準（§7）を満たすようにする。色相は `lib` の純粋関数 `communityHue(id)` で導出する（S2 でテストする）。導出は黄金角（137.508°）で ID を色相環に散らす。

| トークン | 用途 | ライト | ダーク |
|---|---|---|---|
| `--community-ink-l` / `-c` | コミュニティ色の文字（チップ、見出し） | 46% / 0.12 | 80% / 0.11 |
| `--community-mark-l` / `-c` | 欄外罫・角印 | 64% / 0.15 | 70% / 0.14 |
| `--community-paper-l` / `-c` | コミュニティ色の面（予備） | 94.5% / 0.035 | 26% / 0.045 |

### 3.2 書体

| 用途 | 指定 | 備考 |
|---|---|---|
| 和文（本文・見出し） | `"Hiragino Sans", "Noto Sans JP", "Yu Gothic UI", system-ui, sans-serif` | 和文 Web フォントは容量が大きいため読み込まない |
| 欧文・数字（ワードマーク、数値） | **Fraunces**（OFL、可変：wght・opsz、Latin サブセット 65.7KB） | woff2、`font-display: swap`。`public/assets/fonts/` に自前ホスト |

- 数字は `font-variant-numeric: tabular-nums` で桁を揃える。
- 本文は 16px 以上、行間は 1.8 前後。1行の長さは全角35〜40字程度（`max-inline-size` で制御）。
- 和欧混植の約物（括弧、句読点）の詰めは `text-spacing-trim` などのプログレッシブエンハンスメントで扱い、未対応ブラウザでも崩れないようにする。

### 3.3 文字サイズ

比率 1.25 のモジュラースケールを `clamp()` で流体的に定義する（`--step--1` 〜 `--step-5`）。見出しの階層は、大きさの差だけで判別できるようにする。

### 3.4 余白・寸法

| トークン | 内容 |
|---|---|
| `--space-1`〜`--space-10` | 4px 基準の段階（4, 8, 12, 16, 24, 32, 48, 64, 96, 128） |
| `--radius` | 2px 程度。角丸は控えめにする |
| `--line-width` | 1px。罫線で区切り、影は原則使わない |
| `--measure` | 本文の最大行長（38em） |
| `--column` | フォーム・通知・編集パネルの最大幅（42rem）。幅をそろえるために共通で使う |
| `--hit` | 操作対象の最小の高さ（2.75rem = 44px） |

### 3.5 動き

| トークン | 値（初期値） | 用途 |
|---|---|---|
| `--duration-1` | 120ms | ホバー、押下 |
| `--duration-2` | 200ms | 開閉、色の変化 |
| `--duration-3` | 320ms | 画面遷移 |
| `--ease-out` | `cubic-bezier(.2, .7, .2, 1)` | 標準のイージング |

`prefers-reduced-motion: reduce` では、すべての移動・拡大縮小を止め、色の変化のみ残す。

### 3.6 ブレークポイント

モバイルファーストで、`40rem`（タブレット）と `64rem`（デスクトップ）の2点。最小幅 360px で崩れないこと。

## 4. レイアウト

### 4.1 共通

```
┌──────────────────────────────────────────────┐
│ [ワードマーク]   ホーム  コミュニティ   alice │  ← SiteHeader
├──────────────────────────────────────────────┤
│ PageHeader（見出し・説明・主要操作）            │
│                                              │
│ 本文領域（12カラムグリッド。一覧は広め、       │
│ 本文は --measure で行長を制限）                │
├──────────────────────────────────────────────┤
│ SiteFooter（最小限）                           │
└──────────────────────────────────────────────┘
```

- 先頭に「本文へスキップ」リンクを置く。
- 現在地のナビゲーションは `aria-current="page"` で示し、見た目にも反映する。
- ログイン中ユーザーの表示名をヘッダーに表示する。

### 4.2 画面ごとの構成

| 画面 | 構成の要点 |
|---|---|
| ホーム | 大きな見出しの下に、横断のスレッド一覧（コミュニティチップ付き）とページング。紙面の目次として最も編集的に組む |
| コミュニティ一覧 | コミュニティのカード（名前、説明の冒頭、色相）を並べる。ページ見出しの操作として「コミュニティを作る」ボタン（作成ページへのリンク）を置く。空状態からも作成ページへ誘導する |
| コミュニティ作成 | パンくず（コミュニティ）と見出しの下に、名前・説明のフォームを `--column` の幅で置く。400／409 は同じページで入力値とエラー付きで再描画 |
| コミュニティページ | コミュニティ色相を見出しに効かせ、説明、スレッド一覧、スレッド作成フォームを置く。編集・削除は本人のみ |
| スレッドページ | タイトル、本文（先頭の投稿として強調）、返信を時系列で並べ、末尾に返信フォーム。本文は `--measure` で読みやすく |
| エラーページ | 403／404／500／503 を、それぞれ短い説明と戻り先（ホーム）付きで、他の画面と同じ水準で設計する |

## 5. 共通部品

`src/views/components/` に置く。部品は表示に必要な値を props で受け取り、データ取得をしない（ARCHITECTURE §3 の views の責務どおり）。

| 部品 | 使う画面 | 責務・状態 |
|---|---|---|
| `Layout` | 全画面 | `<html lang="ja">`、メタ情報、CSS とフォントの読み込み、スキップリンク |
| `SiteHeader` / `SiteFooter` | 全画面 | ワードマーク、ナビゲーション（現在地）、表示名 |
| `PageHeader` | 全画面 | 見出し、説明、操作（任意） |
| `CommunityChip` | ホーム、スレッドページ | コミュニティ名と色相。リンク |
| `CommunityCard` | コミュニティ一覧 | 名前、説明の冒頭、色相 |
| `ThreadList` | ホーム、コミュニティページ | 一覧、空状態、ページング |
| `ThreadListItem` | 同上 | タイトル、コミュニティチップ（ホームのみ）、作成者、投稿数、最終投稿日時、「編集済み」 |
| `Pagination` | 同上 | 前後のページ、現在ページ。範囲外は空状態と組み合わせる |
| `PostItem` | スレッドページ | 本文／返信の区別、投稿者、日時、「編集済み」、本人の操作。`id="post-:id"` |
| `OwnerActions` | 各画面 | 本人のみ表示。`EditDisclosure`（`<details>` の編集フォーム）と `DeleteButton`（`confirm`） |
| `Field` | 各フォーム | ラベル、入力、補足（上限文字数）、エラー（`aria-invalid`、`aria-describedby`） |
| `FormErrorSummary` | 各フォーム | 400／409 の理由をフォームの先頭にまとめる |
| `Notice` | 各画面 | 削除できない理由（409）などの通知 |
| `Timestamp` | 各画面 | `<time datetime="UTC">` と JST 表示 |
| `EmptyState` | 一覧 | 空のときの説明と次の行動 |
| `ErrorPage` | エラー | 403／404／500／503 |

- スレッド一覧の行は、ホーム（W13）とコミュニティページ（W8）で同じ `ThreadListItem` を使い、差分は props（コミュニティチップの有無）で切り替える。
- テストは CSS クラスや DOM の細部に依存しない（TEST_STRATEGY §3.3）。部品の見た目を変えてもテストが壊れないようにする。

## 6. インタラクションと状態

### 6.1 状態

すべての操作要素に、通常・ホバー・フォーカス（`:focus-visible`）・押下・無効の状態を定義する。

### 6.2 JS を使わない動き

| 対象 | 方法 |
|---|---|
| 画面遷移 | クロスドキュメントの View Transitions（`@view-transition { navigation: auto; }`）。未対応ブラウザでは通常の遷移 |
| 編集フォームの開閉 | `<details>` の開閉に CSS のトランジションを付ける（対応ブラウザのみ） |
| 返信後の位置 | `#post-:id` の `:target` で、該当投稿を一時的に強調する |
| 一覧行のホバー | 色と罫線の変化。レイアウトを動かさない |

### 6.3 網羅すべき状態

次の状態を、すべて意図して設計する（崩れを放置しない）。

- 空の状態：コミュニティ0件、スレッド0件、範囲外のページ
- 入力エラー：400（項目ごとのエラー）、409（名前の重複、削除できない理由）
- エラーページ：403、404、500、503
- 極端なデータ：200字のタイトル、10,000字の本文、改行の多い本文、区切りのない長い文字列（`overflow-wrap: anywhere`）、50字のコミュニティ名
- 件数：1件、20件ちょうど、21件（ページング）
- 本人／他人：操作が出る場合と出ない場合

## 7. アクセシビリティ

WCAG 2.2 の AA を満たす。

- コントラスト比：本文 4.5:1 以上、大きな文字と UI 部品 3:1 以上。ライト・ダーク、全コミュニティ色相で満たす。
- ランドマーク（`header`、`nav`、`main`、`footer`）と、飛ばしのない見出し階層。
- フォームはすべてラベル付き。エラーは色だけでなく文言で示し、`aria-describedby` で入力と結びつける。
- キーボードだけで全操作ができる。フォーカスリングを消さない。
- 操作対象は 24×24 CSS px 以上（モバイルでは 44px を目安にする）。
- 色だけで情報を伝えない（コミュニティ色相は名前と併記する）。

## 8. 実装方針

### 8.1 CSS とアセット

- フレームワークやビルド工程を使わず、手書きの CSS 1ファイルとする。
- `@layer reset, tokens, base, layout, components, utilities;` で詳細度を管理する。
- クラス名は部品単位（例：`.thread-item`、`.thread-item__title`）で付ける。
- CSS とフォントは Workers Static Assets（`wrangler.jsonc` の `assets.directory`）で配信する。Access の内側に置かれるため、外部 CDN には依存しない。
  - ※ ARCHITECTURE §9 の設定に `assets` を追加する。
- クライアント JS は増やさない（削除確認の `confirm` のみ。ARCHITECTURE §2）。

### 8.2 予算

| 項目 | 上限 |
|---|---|
| CSS | 圧縮前 40KB 以下 |
| Web フォント | 合計 100KB 以下（woff2） |
| クライアント JS | 削除確認のインラインのみ |
| 外部リクエスト | なし |
| レイアウトシフト（CLS） | 0 に近づける（フォントのフォールバックの寸法を合わせる） |

### 8.3 スタイルガイドページ

- `GET /_styleguide` に、全部品と §6.3 の状態を固定のサンプルデータで並べたページを置く。
- `AUTH_MODE=dev` のときだけ有効にし、それ以外は 404 を返す（S1 でテストする）。
- 画面の実装前でも、部品の品質をこのページでセルフチェックできるようにする。

## 9. 品質基準とセルフチェック

### 9.1 評価軸

各軸を10点満点で採点する。

| 軸 | 観点 | 確認すること（例） |
|---|---|---|
| A. ビジュアル | タイポグラフィ、余白、配色、グリッド、細部の一貫性 | 階層が書体と大きさだけで読めるか。揃えのずれ、行間・字間の違和感がないか |
| B. 独自性 | コンセプト、シグネチャー | テンプレート感がないか。§2.2 の3要素が効いているか |
| C. 構造 | 発見と一望の導線、情報の優先度、ナビゲーション | ホームで気になるスレッドが拾えるか。現在地と戻り先が明確か |
| D. インタラクション | 状態の網羅、フィードバック、動きの質 | §6 の状態がすべて設計されているか。動きが速すぎず遅すぎないか |
| E. コンテンツ表現 | 極端なデータ、文言 | 長文・空・エラーで崩れないか。文言が短く具体的か |
| F. アクセシビリティ | §7 | axe の違反が0件か。キーボードで全操作できるか |
| G. 技術品質 | §8.2 の予算、HTML の妥当性 | 予算内か。外部リクエストがないか |

### 9.2 合格基準

- 全軸が **8点以上**。
- F と G は、機械的なチェック（axe の違反0件、予算内）を満たす。
- 「この画面を受賞サイトと並べたときに見劣りするか」という問いに、具体的な理由を挙げて「しない」と言える。

### 9.3 キャプチャ条件

| 条件 | 値 |
|---|---|
| ビューポート | 390×844（モバイル）、1440×900（デスクトップ） |
| 配色 | ライト、ダーク |
| 対象 | 対象画面と §6.3 の状態。004b ではスタイルガイドページ |

### 9.4 ループの手順

1. `AUTH_MODE=dev` でローカルサーバーを起動する（`npm run dev`）。
2. 画面用のデータを HTTP 経由で投入する（`npm run design:seed`）。
3. スクリーンショットを撮る（`npm run design:capture`）。保存先は `design/rounds/NN/`。
4. アクセシビリティを機械チェックする（`npm run design:audit`、axe）。
5. スクリーンショットを実際に見て、§9.1 の評価軸ごとに採点し、根拠と改善点を `design/rounds/NN/review.md` に記録する（§9.6 のテンプレート）。
6. 合格基準を満たせば終了する。満たさなければ改善を実装し、`npm test` で回帰がないことを確認して、次のラウンドに進む。
7. **最大5ラウンド**で合格しない場合は、そこで止める。未達の軸、理由、次の打ち手を記録し、ユーザーに判断を仰ぐ。

### 9.5 自己評価の偏りへの対策

- 合格ラウンド以外では、毎回3つ以上の具体的な改善点を挙げる。「良い」「問題なし」だけの評価をしない。
- 前ラウンドのスクリーンショットと並べて比較し、改善が実際に見た目に表れているかを確かめる。
- 可能なら、実装の文脈を持たない別のエージェント（サブエージェントなど）にスクリーンショットと本書だけを渡して採点させ、自己採点と比べる。点差が2点以上ある軸は、低い方を採用する。
- 最終判断はユーザーのレビューで行う。セルフチェックの合格は、ユーザーレビューに出してよい状態を意味する。

### 9.6 review.md のテンプレート

```markdown
# Round NN — <対象>

## スクリーンショット
- mobile-light / mobile-dark / desktop-light / desktop-dark

## 採点
| 軸 | 点 | 根拠 |
```

## 10. ツール

デザインの確認用のツールであり、`npm test` には含めない。振る舞いの検証は TEST_STRATEGY の S1・S2 で行い、ここでは見た目とアクセシビリティだけを確認する（TEST_STRATEGY の「E2E の自動テストは作らない」方針は変えない）。

| 用途 | ツール |
|---|---|
| スクリーンショット | Playwright（Chromium） |
| アクセシビリティの機械チェック | `@axe-core/playwright` |
| スクリプト | `scripts/design/`（`seed`、`capture`、`audit`） |

- スクリーンショット（PNG）は Git に含めない（`.gitignore`）。`review.md` は含め、品質判断の履歴を残す。
